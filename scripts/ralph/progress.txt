## Codebase Patterns
- 后端使用 SQLAlchemy ORM + `create_all` 自动建表，新列需有默认值（`default=None`）
- 前端 Next.js App Router，使用 `@/lib/api.ts` 作为唯一 API 层，所有类型和请求函数集中管理
- `StudentSession` 类型是前后端学生状态的桥梁，新增字段需同步前后端
- 后端 `/students/me` 端点是目标岗位的权威来源，各页面通过 `getStudentSession()` 获取
- 数据库无 alembic 迁移，用 `Base.metadata.create_all` 管理 schema
- `MatchResult` 模型新增列必须带 `default` 值（如 `default=""`, `default=list`, `default=dict`），否则旧数据读取会报错
- 历史记录回放兼容：新字段有 JSON 默认值，旧记录缺字段时用 fallback 查询（如从 `MatchDimensionScore` 表回填 `dimensions_json`）
- `GET /matching/{match_id}` 和 `POST /matching/analyze` 必须返回同一 `MatchingResponse` 结构（student_id, job_code, total_score, weights, dimensions, gap_items, suggestions, summary）
- `PathRecommendation` 新增 JSON 列用 `default=dict`，历史记录缺列时 SQLAlchemy 会用默认空 dict 兼容，无需额外 fallback 查询
- 后端 Pydantic schema 中使用 `Field(alias="from")` 处理 Python 关键字字段名，序列化时用 `model_dump(by_alias=True)` 输出原始键名
- `APIResponse.data` 是 `Optional[Any]`，可以直接接收 Pydantic model 对象，FastAPI 会自动序列化
- 当 service 层函数返回类型从 `dict` 改为 Pydantic model 后，所有使用该返回值的下游代码（如 MockLLMProvider）必须同步更新为属性访问而非字典下标访问
- 匹配评分固定四维：基础要求(0.2)、职业技能(0.4)、职业素养(0.2)、发展潜力(0.2)；OCR 证据作为 evidence 增强折叠到四维中，不作为独立维度展示
- `score_recommended_job()` 返回的 `evidence_boost` 表示 OCR 项目/意向证据加分，总分 = 四维加权平均（含 evidence_boost）
- 报告生成前需通过证据校验门禁（`_check_evidence_sufficiency`），资料不足时返回 `status="insufficient_data"` + `missing_evidence` 列表，前端据此展示明确提示
- `ReportResponse` 中 `content` 和 `markdown_content` 需允许空值（`dict`/`str` 默认值），否则 `insufficient_data` 状态无法通过 Pydantic 校验
- 统一目标岗位解析逻辑提取到 `app.services.student.target_job.resolve_target_job()`，所有需要目标岗位的模块应从此处导入，不要各自实现回退逻辑
