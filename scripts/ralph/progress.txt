## Codebase Patterns
- Report generation must check evidence sufficiency before calling LLM; return `insufficient_data` status instead of pseudo-complete reports.
- MockLLMProvider must never include hardcoded generic fallback text (e.g. industry_trend, generic action plans); derive all content from real data or leave empty.
- Backend uses SQLAlchemy ORM plus create_all; new JSON columns need defaults for backward compatibility.
- Frontend uses Next.js App Router and frontend/lib/api.ts as the single API access layer.
- /students/me is the source of truth for the current target job; writes go through PUT /students/me/target-job.
- Student model stores target_job_code and target_job_title separately from career_goal; frontend reads target_job_code first, then falls back to suggested_job_code.
- /students/me is the source of truth for the current target job, and writes go through /students/me/target-job.
- Path results, history replay, and report pages must share one graph structure instead of building separate view models.
- Report generation must check evidence sufficiency first and return insufficient_data when resume evidence is missing.
- Progress UI state must follow real task state instead of static completed markers.
- OCR failures must distinguish parse errors, service errors, and network or timeout errors.
- PathRecommendation model is the DB backing for career path snapshots; add new JSON columns with `default=dict` for backward compat.
- get_path_result endpoint must provide backward-compatible fallback when graph snapshots are missing from old records.
- CareerPathService.plan_path returns vertical_graph and transition_graph; both must be persisted to PathRecommendation.
- Cross-entity references (e.g. CareerReport -> PathRecommendation) use nullable FK columns to avoid breaking old records; always check null before fetching linked data.
- Report page should fetch graph data via getPathResult(path_recommendation_id) instead of duplicating graph structures in report content_json.
- Target job resolution priority: 手动确认 (target_job_code) > 已确认推荐岗位 (career_goal→JobProfile) > 最近匹配岗位 (MatchResult) > 默认回退 (empty). Backend `resolve_target_job()` in students.py implements this; all pages should use `resolved_job_code` from GET /students/me.
- Vertical graph timeline rendering: use `node.stage === "当前目标" || index === 0` to detect the target node for highlighting.
- Path page must never fall back to plain-text list rendering (primaryPath/alternatePaths); always use graph views or show empty state.
- Chat system must never inject fixed-length career planning templates; system prompts must be evidence-first and template-after.
- _build_user_context should include all available user data: student info, profile, match results (with dimensions), path recommendations, and OCR content.
- Analysis pipeline state is tracked via AnalysisRun model (analysis_runs table) with four states: pending, running, completed, failed. Frontend calls backend step APIs (markStepRunning/markStepComplete/markStepFailed) as each pipeline step executes.
- Pipeline buildSteps() must use "running" status for the current step, not "done"; completed steps are tracked separately via a Set<string> passed as completedKeys parameter.
- Valid pipeline step keys: uploaded, parsed, profiled, matched, reported. These are defined in PIPELINE_STEP_KEYS constant in page.tsx and VALID_STEPS in analysis.py.
- In async pipeline functions, track current step with a local variable instead of reading React state from closure — state updates are async and the closure captures stale values.
